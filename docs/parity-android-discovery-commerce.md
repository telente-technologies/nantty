# React Native ↔ Kotlin Android discovery and commerce parity

**Audit date:** 2026-11-04
**Scope:** Explore/Search, Category, Store, Product, Cart, Checkout, Payment, Orders, Disputes, Wallet.
**Method:** source and route inspection only; no live API requests or production data. The checkout was already dirty, including unrelated changes and untracked Cart work. Those changes were preserved. This report describes the current working tree, not a clean baseline or a release certification.

## One implemented gap: product search to product detail

React Native exposes product search and routes product results to `ProductDetail`; Kotlin previously had no product result type, model, result rendering, or product-result callback. Added:

- `SearchType.PRODUCTS` and a typed `SearchProduct` parser. It ignores wrong-kind/malformed entries, rejects negative/invalid money and unsafe IDs, and validates media URLs through the existing sanitizer.
- An accessible, minimum-size Compose product result row with localized currency formatting, image alt handling, and out-of-stock status.
- Product result pagination/deduplication and navigation into the existing Mart detail route.
- Unit and Compose regression cases for API mapping and result navigation.

This closes the global product-search → detail path only. It does not claim Mart-scoped search, store/profile scope, the other result families, or overall commerce parity.

## Cart compile blocker reported during integration

The current untracked `CartRepository.kt` had `HTTP_UNPROCESSABLE_ENTITY` declared as a private member of the repository class but referenced by the top-level `cartMutationFailureMessage`, making the symbol unavailable at that call site. Moved the constant to file scope as `CART_HTTP_UNPROCESSABLE_ENTITY`; added a regression test that a `422` add-item response still maps to the existing safe unavailable-option message without being treated as an auth failure. This preserves the existing mapping semantics.

## Delta — 2026-11-04: Mart product-detail purchase interaction

Compared `apps/mobile/src/screens/product/productDetail.screen.tsx` and its `OptionSelect` quantity control with `apps/native/android/app/src/main/java/com/nantty/android/ui/MartScreen.kt`, `MartProductDetailScreen.kt`, and the current cart API adapter.

- **Existing parity:** tapping a Mart product opens its detail route in Kotlin; the detail reads the product endpoint, presents the returned variants and stock state, and submits the chosen variant through `POST /api/v1/cart/items`. React Native also navigates from Mart to a product detail and adds a selected product/variant through the cart service.
- **Confirmed gap and fix:** React Native offers quantity choices 1–10 and submits the chosen quantity. Kotlin had no quantity control and always called the cart repository with its default quantity of 1, despite the existing Android repository already supporting a `quantity` request field. Added native decrement/increment controls with the same 1–10 range and now pass the selected quantity to that existing request. No API behavior or prices are fabricated.
- **Still different / not addressed in this slice:** React Native routes to Cart after a successful add; Kotlin currently confirms the add inline. RN also has save/share, reviews, store/brand destinations, related products and reporting interactions that are not present in this Kotlin product-detail screen. These are concrete remaining gaps, not claimed as fixed here.
- **Validation added:** Android UI regression coverage selects quantity 3, submits Add to cart, and checks the captured request body includes `productId` and `quantity: 3`. This test uses a fake transport only at the test boundary; it does not simulate server success semantics beyond the repository's existing result contract.
