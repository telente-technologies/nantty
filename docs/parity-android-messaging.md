# React Native ↔ Kotlin Android messaging parity

Audit date: 2026-11-04  
Scope: React Native messaging screens and service contracts versus the Kotlin Android `Messages` destination, repository, and navigation. This records the repository state, not a live-service or device audit.

## Summary

React Native has a navigable messaging experience spanning inbox, conversation, settings, new-message, group/channel creation, and conversation info. Kotlin Android now supports the Chats/Requests/Spam inbox folders, All/Direct filters in Chats, and the existing accept/not-spam/delete/block request actions, along with a basic thread-read path. It deliberately displays a non-content placeholder for encrypted messages and disables composition because no Kotlin implementation of the React Native key lifecycle, envelope format, decryption, or ratchets is present. This is a safer and broader UI/API foundation, **not E2E messaging parity**.

The high-priority safe fix in this audit is session recovery for Android inbox reads: on one HTTP 401, the repository now asks the existing encrypted session repository to rotate the session and retries the same read once. A revoked session still requests sign-in; a transient refresh failure remains a retryable load failure. The retry is covered by local transport tests. No backend or mobile product code outside the Kotlin messaging/session wiring and its tests was changed for this fix.

## Contracts, session, and encryption

- The backend conversation list is authenticated and supports `folder`, `filter`, cursor, and page size; see `services/typescript/social/src/modules/conversations/controllers/conversations.controller.ts` (`list`) and `services/typescript/social/src/modules/conversations/queries/listConversations/listConversations.handler.ts`. Kotlin now calls the chats filter or the requests/spam folder parameters, sends the access token as a Bearer token, and validates cursors before the request. The existing backend accept, not-spam, delete, and block routes are called from folder actions.
- React Native's API client has shared refresh-on-401 handling (`apps/mobile/src/services/core/apiClient.service.ts:40-58,105-139`). Kotlin already owns refresh-token rotation and encrypted persistence in `AccountSessionRepository.kt:82-104`, but the original inbox reader did not use it after a 401. This audit now wires that refresh callback from `NanttyApp.kt:263-268` and retries once in `MessagesRepository.kt:50-65`.
- React Native messaging encrypts outgoing payloads before POST and decrypts message pages after GET (`apps/mobile/src/services/chat/messages.service.ts:53-65,102-113`); its crypto client is in `apps/mobile/src/services/chatCrypto/chatCrypto.service.ts`. Kotlin has no corresponding message crypto implementation in this scope. Message body previews therefore remain omitted by Kotlin rather than treating server fields as plaintext. **Do not claim Android E2EE parity.**
- The key-directory contract has now been traced end to end. RN registers with `PUT /api/v1/chat/keys/devices/{deviceId}`, checks status with `GET` on that path, rotates signed prekeys with `PUT .../{deviceId}/signed-prekey`, uploads one-time prekeys with `POST .../{deviceId}/prekeys`, queries recipient devices with `POST /api/v1/chat/keys/devices/query`, claims bundles with `POST /api/v1/chat/keys/bundles`, and uses the mailbox endpoints for group key distribution. Social mounts these routes in `services/typescript/social/src/modules/messagingKeys/routes/messagingKeys.routes.ts`; RN paths and request types are in `packages/chatCrypto/src/directory.ts`. Kotlin currently calls none of them. A backend accepting `protocol: "signal-v1"` only stores opaque ciphertext; it does not establish cross-client compatibility.
- RN key-state lifecycle is also more than a keystore keypair: secure storage holds device identity, signing secrets, signed-prekey private material, and group keys; its encrypted record store holds ratchet sessions, one-time-prekey private material/counters, peer identity trust, sender-key state, and expiring decrypted-message cache (`packages/chatCrypto/src/protocolStore.ts`, `apps/mobile/src/services/chatCrypto/mobileKeyStore.ts`). Android now has a durable encrypted `ChatCryptoStorage` backend in `security/chatcrypto/` with separate `secrets`/`records` namespaces, SQLite ciphertext rows and Android Keystore AES-GCM with namespace/key-bound AAD. It is not yet wired to the protocol store or messaging lifecycle; sign-out/device-removal semantics must be resolved before device registration, or logout/reinstall could strand or desynchronize ratchets.
- **Interoperability is unproven beyond primitives.** The RN package has seeded protocol tests, but no shared deterministic full-session fixture consumed by Kotlin. Porting should proceed through fixture-backed stages (device identity and registration, X3DH/prekey wire messages, ratchet turns/replay/out-of-order handling, envelope/payload binding, then groups/mailbox). Keep decrypt/send disabled until these pass in both runtimes; do not label this custom `signal-v1` implementation as libsignal-compatible.
- Kotlin now has a small primitive compatibility layer in `apps/native/android/app/src/main/java/com/nantty/android/security/chatcrypto/ChatCryptoPrimitives.kt` (Bouncy Castle 1.86): Ed25519/X25519 operations, Ed-to-X identity conversion, HKDF-SHA256, HMAC-SHA256, AES-256-GCM, strict standard Base64, and big-endian uint32 helpers. Its unit tests reproduce the existing RFC primitive vectors, and additionally assert the Ed→X public/private consistency property. This is not the X3DH/ratchet/envelope protocol and is not enough to enable key registration, decrypt, or send.
- React Native has real service calls in the production screen/service path. Repository fixtures, mocks, and tests exist separately; they are not evidence of live delivery or encryption interoperability. The Android tests added/used here use an in-process fake `MessagesTransport`, not a public or staging API.

## Implemented remediation and verification

**2026-11-04 — All/Direct inbox filter parity:** the Android inbox exposes accessible Material 3 All/Direct tabs and sends the selected filter through `GET /api/v1/conversations?filter=all|direct&limit=20`. Switching filters clears prior rows and pagination state; responses from a previously selected filter are ignored so a slower request cannot replace the current results. The default remains All.

Fresh serialized verification on 2026-11-04: `:app:testDebugUnitTest`, `:app:compileDebugKotlin`, and `:app:compileDebugAndroidTestKotlin` passed; the unit XML reports **236 tests, 0 failures, 0 errors**. Compose test sources compiled but were not run: `adb devices -l` returned no device. Compiler emitted existing deprecation warnings. No live API or production data was used.

**Fix: one-time refresh-and-retry for an expired Android inbox access token.** A 401 causes `AccountSessionRepository.refreshSession()` to rotate and persist tokens, then the same inbox GET is retried once with the new access token. A missing/invalid refresh session yields `authenticationRequired=true`; other refresh errors remain ordinary retryable failures and do not trigger forced sign-out. A second 401 is surfaced as authentication-required; no retry loop is possible.

Regression coverage in `apps/native/android/app/src/test/java/com/nantty/android/data/MessagesRepositoryTest.kt` covers successful refresh/retry, failed/revoked refresh without a second request, and transient refresh failure without misclassifying the session as revoked. The final integrated run of `:app:compileDebugKotlin`, `:app:testDebugUnitTest`, and `:app:compileDebugAndroidTestKotlin` completed successfully: **195 unit tests passed, 0 failed, 0 errored**, and Android instrumentation-test sources compiled. No emulator/device or live API was used.

**Thread-read and primitive foundation added in the current work:** tapping an inbox row opens the Compose thread and supports system Back; history is fetched from the authenticated endpoint, the conversation is marked read, and pagination metadata is validated. The repository model has no plaintext field. The view shows only “encrypted content unavailable” placeholders and keeps compose disabled until interoperable Kotlin crypto is actually implemented. The combined verification `./gradlew :app:testDebugUnitTest :app:compileDebugKotlin :app:compileDebugAndroidTestKotlin` now succeeds: 207 JVM unit tests passed (including four thread repository and eight crypto primitive tests), Kotlin app sources compiled, and Android UI-test sources compiled. No emulator/device or live API was used, so Compose instrumentation tests were **not executed**.

**2026-11-05 — conversation search and direct start:** Android Messages now provides a debounced, accessible search for server-returned direct conversations and people. Selecting an existing conversation opens its thread; selecting a person creates/resolves the direct conversation through the existing backend endpoint before opening it. Search and start calls use the current access token and one refresh-and-retry on 401. Query length and IDs are bounded/validated, avatars must use HTTPS, and response snippets are intentionally ignored so encrypted content cannot leak. The search UI, data contract and repository were separated from the inbox screen/repository; affected Kotlin files are 118–369 lines. The earlier 301-test verification and remaining gaps are preserved in the preceding log. This does not add encrypted group-title search, group/channel creation, conversation info/actions, or E2E encryption.

**2026-11-05 — Requests/Spam inbox parity slice:** Kotlin now selects the backend-supported `folder=requests|spam` list contract and keeps All/Direct filtering scoped to Chats. Request rows show the privacy explanation and accept/delete/block actions; spam rows show server-provided `spamReason` when present, plus not-spam/delete/block actions. Block requires confirmation. Each mutation validates the conversation UUID, uses the existing authenticated Social endpoint and retries once after session refresh; folder changes and mutations reload from server state. Thread reads now follow RN’s privacy rule: requests/spam conversations do not send read receipts and the mark-read control is hidden. Unit tests cover exact folder paths, metadata parsing, validated IDs and 401 retry; Compose regression sources cover folder selection/accept and the read-receipt guard. No new backend route was added. The messaging inbox remains partial: reporting, report-and-block, cached first paint, story tray, groups/channels and settings actions remain RN gaps. Thread E2E encryption remains the critical conversation blocker.

**2026-11-05 — `signal-v1` serialization foundation (not yet integrated):** Kotlin now has typed direct/group envelope and inner-payload codecs in `security/chatcrypto/SignalV1EnvelopeCodec.kt` and `SignalV1PayloadCodec.kt`. A single shared JSON fixture at `packages/chatCrypto/fixtures/signal-v1-serialization.json` is consumed by RN tests and Android's `SignalV1CodecTest`; direct/group envelopes and a payload are checked against the same wire representation, avoiding duplicate fixtures. Strict type checks reject string-coerced and out-of-range protocol versions; payload sanitization follows RN. This does **not** add device registration, encrypted persistence, X3DH, ratchets, message send/decrypt, or UI changes. The existing secure-unavailable thread state remains correct. A seeded RN ratchet-vector assertion was stale after the protocol KDF label changed from Zudomart to Nantty; I updated the expected deterministic ciphertext. Kotlin's live-location sanitizer now also accepts timezone-free ISO local date-times, which RN's `Date.parse` accepts; a shared behavioral test guards this edge. Latest validation: `pnpm --filter @nantty/chat-crypto test` (**93/93**) and typecheck pass; pnpm reports the environment's existing Node 24.19 versus required >=26.13 engine mismatch. Android `:app:compileDebugKotlin` plus focused `SignalV1CodecTest` passes (**11/11**); the latest full Android JVM suite passed (**382/382**), and `:app:lintDebug` passed with 0 errors (existing warnings remain). No device/instrumentation test or live API integration was run. The overall E2E protocol remains incomplete; do not enable sending/decryption yet.

Corrupt, truncated, unknown-version, or cross-key/namespace ciphertext fails closed. ## Recommended next order

1. Extend shared deterministic protocol fixtures to X3DH/prekey and ratchet messages; do not claim generic Signal/libsignal interoperability and do not enable plaintext sending.
2. Wire the encrypted Android storage backend into the protocol-store contract and define logout/device-removal semantics; then implement device registration, signed/one-time prekeys, X3DH, pairwise ratchet operation, trust-change handling, and cross-client direct-message conformance tests before enabling decrypt/send.
3. Add group sender-key/mailbox flows and encrypted media only after direct-message interoperability passes; then add real-time and retry/idempotency semantics.
4. Add report/report-and-block, cached first paint, story tray, groups/channels, conversation info, preferences, local encrypted cache/expiry, and remaining chat-safety flows.
5. Add adaptive list/detail navigation on expanded windows after functional thread support. Keep compact navigation, touch, keyboard/IME, focus, semantic labels, resizing, and font scaling in coverage.

These recommendations follow Android's guidance to support multiple form factors with adaptive window-based layouts, rather than assuming device classes: [Android getting-started overview](https://developer.android.com/get-started/overview), [Android UI design](https://developer.android.com/design/ui), and [Compose adaptive apps](https://developer.android.com/develop/ui/compose/layouts/adaptive/get-started-with-adaptive-apps).
