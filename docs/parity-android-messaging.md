# React Native ↔ Kotlin Android messaging parity

Audit date: 2026-11-04  
Scope: React Native messaging screens and service contracts versus the Kotlin Android `Messages` destination, repository, and navigation. This records the repository state, not a live-service or device audit.

## Summary

React Native has a navigable messaging experience spanning inbox, conversation, settings, new-message, group/channel creation, and conversation info. Kotlin Android now has an authenticated inbox and a basic thread-read path with system-back navigation and read receipts. It deliberately displays a non-content placeholder for encrypted messages and disables composition because no Kotlin implementation of the React Native key lifecycle, envelope format, decryption, or ratchets is present. This is a safe UI/API foundation, **not E2E messaging parity**.

The high-priority safe fix in this audit is session recovery for Android inbox reads: on one HTTP 401, the repository now asks the existing encrypted session repository to rotate the session and retries the same read once. A revoked session still requests sign-in; a transient refresh failure remains a retryable load failure. The retry is covered by local transport tests. No backend or mobile product code outside the Kotlin messaging/session wiring and its tests was changed for this fix.

## Contracts, session, and encryption

- The backend conversation list is authenticated and supports `folder`, `filter`, cursor, and page size; see `services/typescript/social/src/modules/conversations/controllers/conversations.controller.ts` (`list`) and `services/typescript/social/src/modules/conversations/queries/listConversations/listConversations.handler.ts`. The implemented Kotlin inbox uses the supported chats/all slice only. It sends the access token as a Bearer token and validates cursors before the request (`MessagesRepository.kt:44-65,118-120`).
- React Native's API client has shared refresh-on-401 handling (`apps/mobile/src/services/core/apiClient.service.ts:40-58,105-139`). Kotlin already owns refresh-token rotation and encrypted persistence in `AccountSessionRepository.kt:82-104`, but the original inbox reader did not use it after a 401. This audit now wires that refresh callback from `NanttyApp.kt:263-268` and retries once in `MessagesRepository.kt:50-65`.
- React Native messaging encrypts outgoing payloads before POST and decrypts message pages after GET (`apps/mobile/src/services/chat/messages.service.ts:53-65,102-113`); its crypto client is in `apps/mobile/src/services/chatCrypto/chatCrypto.service.ts`. Kotlin has no corresponding message crypto implementation in this scope. Message body previews therefore remain omitted by Kotlin rather than treating server fields as plaintext. **Do not claim Android E2EE parity.**
- Kotlin now has a small primitive compatibility layer in `apps/native/android/app/src/main/java/com/nantty/android/security/chatcrypto/ChatCryptoPrimitives.kt` (Bouncy Castle 1.86): Ed25519/X25519 operations, Ed-to-X identity conversion, HKDF-SHA256, HMAC-SHA256, AES-256-GCM, strict standard Base64, and big-endian uint32 helpers. Its unit tests reproduce the existing RFC primitive vectors, and additionally assert the Ed→X public/private consistency property. This is not the X3DH/ratchet/envelope protocol and is not enough to enable key registration, decrypt, or send.
- React Native has real service calls in the production screen/service path. Repository fixtures, mocks, and tests exist separately; they are not evidence of live delivery or encryption interoperability. The Android tests added/used here use an in-process fake `MessagesTransport`, not a public or staging API.

## Implemented remediation and verification

**Fix: one-time refresh-and-retry for an expired Android inbox access token.** A 401 causes `AccountSessionRepository.refreshSession()` to rotate and persist tokens, then the same inbox GET is retried once with the new access token. A missing/invalid refresh session yields `authenticationRequired=true`; other refresh errors remain ordinary retryable failures and do not trigger forced sign-out. A second 401 is surfaced as authentication-required; no retry loop is possible.

Regression coverage in `apps/native/android/app/src/test/java/com/nantty/android/data/MessagesRepositoryTest.kt` covers successful refresh/retry, failed/revoked refresh without a second request, and transient refresh failure without misclassifying the session as revoked. The final integrated run of `:app:compileDebugKotlin`, `:app:testDebugUnitTest`, and `:app:compileDebugAndroidTestKotlin` completed successfully: **195 unit tests passed, 0 failed, 0 errored**, and Android instrumentation-test sources compiled. No emulator/device or live API was used.

**Thread-read and primitive foundation added in the current work:** tapping an inbox row opens the Compose thread and supports system Back; history is fetched from the authenticated endpoint, the conversation is marked read, and pagination metadata is validated. The repository model has no plaintext field. The view shows only “encrypted content unavailable” placeholders and keeps compose disabled until interoperable Kotlin crypto is actually implemented. The combined verification `./gradlew :app:testDebugUnitTest :app:compileDebugKotlin :app:compileDebugAndroidTestKotlin` now succeeds: 207 JVM unit tests passed (including four thread repository and eight crypto primitive tests), Kotlin app sources compiled, and Android UI-test sources compiled. No emulator/device or live API was used, so Compose instrumentation tests were **not executed**.

## Recommended next order

1. Port the existing Nantty custom `signal-v1` protocol exactly, beginning with shared deterministic fixtures and cryptographic primitive vectors; do not claim generic Signal/libsignal interoperability and do not enable plaintext sending.
2. Add device registration, signed/one-time prekeys, X3DH, pairwise ratchet persistence, envelope/payload serialization, trust-change handling, and cross-client direct-message conformance tests before enabling decrypt/send.
3. Add group sender-key/mailbox flows and encrypted media only after direct-message interoperability passes; then add real-time and retry/idempotency semantics.
4. Add new-message search/direct start, groups/channels, requests/spam actions, conversation info, preferences, local encrypted cache/expiry, and report flows.
5. Add adaptive list/detail navigation on expanded windows after functional thread support. Keep compact navigation, touch, keyboard/IME, focus, semantic labels, resizing, and font scaling in coverage.

These recommendations follow Android's guidance to support multiple form factors with adaptive window-based layouts, rather than assuming device classes: [Android getting-started overview](https://developer.android.com/get-started/overview), [Android UI design](https://developer.android.com/design/ui), and [Compose adaptive apps](https://developer.android.com/develop/ui/compose/layouts/adaptive/get-started-with-adaptive-apps).
