# Transaction boundaries

> **Provider (owner, 2026-10-11):** Flutterwave is the only payment provider; current provider calls are in [`flutterwaveMigration.md`](../integrations/flutterwaveMigration.md).

As of 2026-10-03. The go-money code (payments, escrow, wallet, ledger) was being edited by another agent while this audit ran (Bachs connected-account mirror: `paymentCollectionPosting.service.go`, `providerMirrorReconciliation.service.go`, `escrowChargebacks.service.go`). Statements below describe the working tree at audit time; re-verify line numbers before acting. Paths are relative to `services/go/modules/`.

> **Bachs and Anchor dropped.** The audit below describes the code as it was (Bachs mirror). Target model (`docs/integrations/flutterwaveMigration.md` §2–3): Nantty holds no customer money; escrow is locked in the buyer's own Flutterwave payout subaccount and released PSA → PSA, then the 24h seller lock applies before a withdrawal transfer; the ledger is the source of truth for what money means. Wherever this file says Bachs, read the Flutterwave equivalent given in brackets.

## 1. Shared machinery (EXISTING)

| Mechanism | Where | Behaviour |
| --- | --- | --- |
| Money transaction | `ledger/src/databases/moneyTransaction.database.go` `RunInMoneyTransaction` | `BEGIN ISOLATION LEVEL READ COMMITTED`; retries the whole closure up to 5 times on `40001` (serialization) and `40P01` (deadlock) with 5·n² ms backoff; any other error rolls back. `23505` is **not** retried. |
| One tx across money schemas | `svc_money` role (member of svc_payments, svc_wallet, svc_ledger, svc_escrow, svc_creators, ...) + `AcquireSharedMoneyDatabase` (one pool, 40 conns) + `EntDriverBoundToTransaction` | payments, escrow, wallet, creators and ledger ent clients all write through the same `*sql.Tx`, schema-qualified via ent `SchemaConfig` |
| Ledger posting | `ledger/src/modules/journal/services/ledgerPosting.service.go` `PostBalancedJournalEntry` | 1) validate balanced lines; 2) `pg_advisory_xact_lock(hashtextextended('ledger-reference:'+reference))`; 3) if `journal_entries.reference` exists → replay (idempotent, request must match); 4) upsert missing accounts `ON CONFLICT (code, currency) DO NOTHING`; 5) `SELECT ... FOR UPDATE` each account **sorted by (code, currency)**; 6) compute new balances, reject negative unless `allow_negative_balance`; 7) `UPDATE ledger_accounts ... WHERE id = ? AND version = ?` (optimistic check under the lock); 8) insert entry + lines with `balance_after_minor` |
| SQL idempotency | `ledger/src/utils/idempotentCommand.util.go` `RunIdempotentMoneyCommand` + `idempotencyRecord.util.go` | `INSERT INTO <schema>.idempotent_requests ... ON CONFLICT (scope, key) DO NOTHING` inside the money tx; a concurrent duplicate blocks on the unique index until the first commits, then replays the stored response; different request hash → `ErrIdempotencyKeyReused` |
| Valkey idempotency | `platform/idempotency/idempotency.store.go`, used by live HTTP gift routes | front-door dedupe only (`SETNX` in-flight / completed). DB unique keys remain the guard. |
| Outbox | `ledger/src/events/outbox.event.go` (money), generated `OutboxEvent` (others) | Insert in the same tx as the state change. Relay: `SELECT ... WHERE published_at IS NULL AND dead_lettered_at IS NULL AND (next_attempt_at IS NULL OR next_attempt_at <= now) ORDER BY created_at LIMIT n FOR UPDATE SKIP LOCKED`, publish to RabbitMQ (confirmed), mark published; 10 failures → dead letter |
| Business-key advisory locks | creators `gift:<sender>:<key>`, `battle-settle:<battleId>`; live `engagement:<user>:<action>` | serialise duplicate requests before the existence check |
| Row locks + version | escrows, payment_intents, withdrawals, payment_refunds, connected_accounts, disputes | `SELECT ... FOR UPDATE` then `UPDATE ... WHERE version = ?` + `version = version + 1` |
| Sweeps | escrow auto-release, seller credit maturity, payout claim, outbox relay | one row per tx, `FOR UPDATE SKIP LOCKED`, so N workers can run safely |

Why READ COMMITTED is acceptable here: every decision that matters is taken on rows locked `FOR UPDATE` (accounts, escrow, intent, withdrawal) or protected by a unique index (reference keys). Reads done **before** taking those locks are the weak spots (section 6).

## 5. Double-spend prevention

| Threat | Control (EXISTING unless noted) |
| --- | --- |
| Same request twice (retry, double tap) | `idempotent_requests` / gift UQ / journal `reference` UQ, all inside the same tx as the effect |
| Two different requests racing on one balance | ledger account `FOR UPDATE` + `version` + `CHECK (allow_negative_balance OR balance_minor >= 0)` → second request sees the first's debit, fails with insufficient balance |
| Deadlock between two postings | accounts locked in sorted order within a posting; across several postings in one tx order is posting order → deadlocks possible, retried on `40P01` (5 attempts) |
| Same webhook twice / concurrently | `webhook_events` UQ; intent `FOR UPDATE` + status check (`isSettleable`) |
| Buyer pays twice for one subject | second success detected (`paidElsewhere`) → marked `duplicatePaymentRefunded` → automatic refund. Race: two intents settling at the same instant both see no other success under READ COMMITTED; for checkouts the second then fails on `escrow_order_id` UQ (`23505`, not retried) and is refunded on webhook redelivery. **Fix (P2):** `pg_advisory_xact_lock('pay-subject:'+purpose+':'+subject_id)` in initialize and settle |
| Withdrawal above provider-held funds | ledger available check + `providerAvailable < amount` per request. Gap: the provider check does not subtract other queued withdrawals still inside the provider balance (`seller:<id>:reservedPayout`), so two requests can each pass. **Fix (P2):** compare against `providerAvailable − reservedPayout balance` under the account lock |
| Payout sent twice | claim with `SKIP LOCKED` + status machine; Flutterwave transfer `reference = wd-<uuid>`, sent once; an unknown outcome is resolved by a GET by reference; finalizer re-fetches by reference before deciding |
| Refund above captured amount | `payment_intents` `CHECK (refunded_minor <= amount_minor)` + intent `FOR UPDATE`; `escrows` `CHECK (refunded_minor <= amount_minor)` |
| IAP receipt replay | `store_purchases` UQ |
| Coins spent after IAP refund | clawback → `UserCoinDebtAccount` + `wallet_risk_flags` |
| Escrowed funds leave early | Escrow is locked by the ledger in the buyer's own PSA; only go-money holds the secret key, NAT IPs are whitelisted, every PSA debit is pre-checked against the PSA balance, and the daily recon freezes wallets on mismatch. PSAs cannot be frozen at Flutterwave, so a court order or deposit reversal can still pull locked money (accepted risk, §3.3 of the spec) |
