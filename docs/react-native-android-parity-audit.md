# React Native ↔ Android Kotlin parity audit

**Audit date:** 2026-11-06
**Scope:** `apps/mobile` React Native app versus `apps/native/android` Kotlin/Jetpack Compose app. This is a source and route audit; it is not a claim of production, device, or backend verification.

## Method and status vocabulary

Compared screen files, React Navigation route registrations, Android root destinations and Compose screens, API/repository contracts, and existing platform parity notes. Route/component existence alone is not evidence of working behavior; rows should be traced through navigation, state, service, authorization, errors, and tests.

- **Implemented (source):** user path and relevant data contract exist in Kotlin source; runtime still needs device/API checks.
- **Partial:** some actions or states exist, but the RN journey has meaningful omissions.
- **Missing:** no equivalent reachable Android path was found in this pass.
- **Intentional:** a platform-specific interaction is acceptable if the user outcome is preserved and documented.
- **Unverified:** source/tests exist but execution against a device, isolated service, or real provider was not performed.

### Current source corrections (2026-11-04)

The initial route-family table above is a baseline, and portions became stale as parallel slices landed. Current source evidence should be interpreted with these corrections:

- **Feed topics:** Android now loads the signed-in followed-topic list, renders selectable For You chips, carries `topicId` through first-page and continuation requests, and clears it when switching feed mode. See `FeedRepository.kt`, `FeedTopicSelector.kt`, and the feed section in `NanttyApp.kt`; unit and Compose-test source exists. This closes topic-filter parity at source level, not device-level.
- **Search scope:** signed-in recent searches can be loaded, recorded on explicit submit/result open, selected, removed, and cleared; guest history requests are suppressed. Kotlin supports global/Mart/store result scopes and now enters profile scope from public profiles with matching All/Posts/Clips/Products tabs. Current-user profile and store-page entry points, plus other result destinations, remain gaps.
- **Cart/checkout/payment:** product detail can add an available variant; cart can load, display server totals, update quantity, remove a line, and refresh. Kotlin also has an initial checkout/payment path: saved-address selection, server quote, idempotent escrow-default checkout, hosted payment initialization, and bounded server-status polling after provider return. Native address management, direct/saved-card/provider-wallet options, provider deep-link restoration, complete purchase recovery, dispute, and seller-order operations remain incomplete. Android is not at full purchase parity.
- **Messaging:** inbox rows open a thread, history is fetched, and the thread is marked read. The thread does not render server ciphertext as plaintext; send stays disabled pending full Kotlin compatibility with RN's custom device/key/session/envelope protocol and cross-client tests. There is no Signal/libsignal compatibility claim.
- **Follow-request routing and row behavior:** Kotlin resolves `kind=followRequest` before a post fallback and returns to Profile with visible or system Back. The inbox constrains content to 720dp, adjusts wide-window padding, labels requester profile/action/loading controls, and opens the requester through the existing public-profile callback. Instrumentation source covers request actions, requester navigation, and notification precedence; it was compiled, not device-run. Announced action success/failure and connected-device verification remain open.
- **Conversation notification target:** when an activity notification includes both a conversation target and a post target, Kotlin now gives the conversation target precedence, fetches it through the authenticated `GET /api/v1/conversations/{id}` contract, then follows older authenticated history (maximum 10 pages) for a validated `messageId` and scrolls/highlights it without exposing ciphertext. URL-only chat target routing and targets outside the bounded history window remain gaps; no device/backend journey was run.
- **Home wallet preview (historical correction):** an earlier serialized verification referred to a Kotlin-only preview as a React Native parity target. Current RN `HomeScreen`/`FeedTab` contain no wallet preview, and the current Kotlin home feed contains none either. Wallet remains a separate RN and Kotlin destination. Do not restore a wallet card only on Android; reconsider it only as a deliberate product change implemented consistently across clients.

The serialized Gradle run for this continuation passed Kotlin compilation, **267 JVM tests** (0 failures/errors), and Android instrumentation-source compilation. No emulator/device was attached, so instrumentation tests and adaptive UI behavior were not executed. These updates do not close the wider route inventory. Source or test-file existence is not equivalent to runtime, backend, payment-provider, accessibility-service, or adaptive-device verification.

### Deep scan follow-up (2026-11-04)

Five focused source audits compared auth/guest, feed/social, commerce, messaging/account, and creator/seller/logistics journeys. The highest-priority findings are:

1. **P1 — checkout/payment parity is partial, not absent.** Kotlin has an escrow-default checkout and hosted payment verification slice, including bounded server-status polling after app resume (3-second interval, 120-second window), offline-aware retry, cancellation, and server-confirmed paid-success actions for payment protection/order detail/Mart. Native address management, RN payment choices, provider deep-link restoration, broader order recovery, and seller operations are still missing. Preserve server-calculated totals, authorization, and idempotency; never simulate payment success. Hosted-provider return is not device-verified.
2. **P0 — messaging is receive-limited, not E2E parity.** Kotlin can open a conversation, fetch history, and mark it read, but cannot safely decrypt/send using RN-compatible device/key/session/envelope behavior. The composer remains disabled, there is no WebSocket/reconnect parity, and inbox request/search/group flows are absent. Keep encrypted payloads hidden until protocol conformance is established.
3. **P1 — guest action replay is missing.** Android routes protected guest actions to auth but does not retain and replay the pending action/return destination as RN does. Public guest route coverage is also narrower.
4. **P1 — social onboarding's birthday challenge is now source-aligned.** RN and Kotlin handle the backend's first-time Google `BIRTHDAY_REQUIRED` challenge; RN supports Google and Apple with a transient birthday prompt/retry, while Android keeps Apple unavailable. Local RN service/onboarding tests pass. The backend auth integration test exists but was skipped because local PostgreSQL was not reachable, so the backend flow is not runtime-verified here. OAuth audience/provider setup and connected-device sign-in remain unverified.
5. **P1 — seller/creator operations and media journeys are substantially incomplete.** Read-only seller/creator/ads workspaces and acting-profile switching now exist. Android creator application submit/status/reapply is now wired, but sample uploads, payout selection, affiliates/subscriptions and approved-creator management remain incomplete. Live, Clips, Stories, Spaces, and seller onboarding/catalog/order/document/logistics operations also lack complete native equivalents. Some RN capabilities are themselves mock/demo or provider-config dependent; reports must distinguish those from production integrations. Seller logistics tracking metadata entered in RN is not evidence of a courier API integration.
6. **P1 — discovery and social creation are narrower.** Explore landing sections and global/Mart search exist, but route-supplied contextual scopes and several result destinations remain absent. Android category search opens focused category browsing within the Mart shell; the landing page exposes the three supported RN collections, but Back does not restore RN's prior Search route. Public profile omits several content/store tabs. Post creation now supports the RN audience choice, but still lacks media/mention/quote/draft/scheduling and other post kinds. Comments and core feed have partial parity, not full feature equivalence.
7. **P1/P2 — wallet, orders, and account controls are partial.** Kotlin wallet is read-only; order lifecycle/dispute/escrow and seller operations are incomplete. General connections, notification follow-request/deep-link targets, broad privacy/security/account management, support workflows and device push registration are also missing or partial; a private-profile follow-request review slice now exists.

The first bounded remediation in this pass is the direct Android sign-in surface: the Kotlin sign-in screen now exposes Google when the Android server client ID is configured, invokes the existing Credential Manager flow, displays provider errors, and hides the option when unconfigured. Focused Compose test source verifies visibility/callback and the missing-config case. General guest-action replay remains an open cross-client gap.

This table is a baseline, not a line-by-line closure. The domain workstreams are adding evidence at screen/flow granularity and implementing bounded fixes in separate reports.

## Cross-cutting quality observations

1. **Navigation is the first parity bottleneck.** Screen components are not enough: destinations absent from the Android shell cannot be reached as user flows. The main Android shell has a different bottom-nav information architecture from React Native, which is acceptable only if equivalent tasks remain discoverable.
2. **Backend/API parity is not UI parity.** Existing API methods (for example cart/order actions or social providers) must not be reported as usable until a reachable Android flow handles loading, error, auth, cancellation, and success states.
3. **No-hardcoding review is still in progress.** Audit config/endpoint origins, business policy values, labels, route IDs, demo content and fallback behavior per domain. UI copy and design tokens can be constants; endpoint origins, user/account values, financial policy, availability and server-controlled eligibility must not be invented in Compose.
4. **Mocks and fixtures are not production integrations.** Every report should label mock-only, source-wired, API-contract-tested, emulator-tested, and staging-tested separately.
5. **Platform differences:** Android should use Material controls, predictive/system Back, accessible semantics and layouts that adapt to window size/posture/input. Pixel-matching RN is not the goal; equivalent task outcomes and clear differences are. Android’s official overview describes phone through tablet/foldable support and modular/testable apps; its UI guide emphasizes native components, adaptive layouts, interaction patterns and accessibility.
