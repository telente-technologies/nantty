# React Native ↔ Kotlin Android commerce and wallet parity

**Audit date:** 2026-11-05
**Scope:** Cart, checkout, payment, buyer order history/detail/disputes, seller order flow, and wallet.  
**Method:** Source inspection of React Native screens/services/types, Kotlin Compose screens/repositories/routes, and Go HTTP route/DTO contracts. This is a static source audit: no live API, account, payment, or production data was used.

## Executive result

Parity is partial. Android can browse Mart, add a selected product variant, list buyer orders, open buyer-order detail, confirm receipt for shipped/delivered orders, and view wallet summary/transactions/escrow holds. The authenticated Compose cart review/quantity/remove flow is implemented. This continuation adds dynamic address creation during checkout, removing the former requirement that buyers create an address on web first.

Android now has an initial checkout/payment UI, can create and select a shipping address via the same API-backed geographic catalogue, and uses server shipping quotes. Buyer dispute opening, evidence upload, dispute detail/status/evidence display, and text messages are now wired from order detail. Seller order list/detail and shipment submission are implemented; this continuation adds the seller escrow payout summary and release-progress timeline to detail. It is not equivalent to React Native and is not purchase-ready for parity sign-off: device-executed flow verification and several purchase recovery/payment options remain. RN has a disputes service method but no visible standalone dispute-record list; do not count that unused API helper as a missing Android screen. Payout-account management is now implemented at source level; withdrawal, funding, provider-wallet, and coin/reward flows are still absent.

### Payout-account management slice — 2026-11-05

RN's payout screen loads saved accounts, searches an API-returned bank list, adds a 10-digit account, and confirms removal. Add/remove run through the step-up sheet, which supports a password proof or email OTP (`purpose: login`) followed by `POST /api/v1/auth/step-up`. Go confirms authenticated `GET /api/v1/banks`, authenticated list, and single-use step-up middleware on both mutations; add's handler is naturally duplicate-safe by user/bank/account fingerprint and returns the existing account. RN's add payload is exactly `{ bankCode, accountNumber }`: there is no `Idempotency-Key`, and the route does not mount idempotency middleware. The payout handler defaults omitted country to `NG`.

Android now exposes a payout-account management view from Wallet, loads the accounts and bank catalogue from those endpoints, filters the returned banks, validates the 10-digit account number, and supports add/remove with fresh password/email-code step-up. The token remains only in short-lived in-process request state and is not written to preferences, saved state or disk; the mutation sends only `X-Step-Up-Token` and mirrors RN's request body without inventing an idempotency header. Account names are not exposed in the list UI, matching RN's display.

`PayoutAccountsRepositoryTest.kt` covers list/bank response parsing, exact authenticated routes, request fields and headers, delete, both step-up paths and local validation. The test file is added but **not run yet**: no Gradle job is active, and the shared Android source currently has an unrelated compile blocker in `SignedInPaymentDestination.kt`, whose callsite still supplies removed `CheckoutPaymentScreen` parameters (`onViewOrders`) and omits the new required callbacks. This wallet task intentionally leaves checkout/payment files unchanged; the assigned shared-checkout owner should resolve that before the coordinated full Gradle run. No device/live-wallet verification has been performed. Withdrawals, default-account controls, funding, provider-wallet and rewards remain outside this slice.

## Implemented gap: authenticated cart review and line management

**Why this was selected:** React Native exposes the cart as the handoff between product discovery and checkout. Android previously showed “Added to your cart” after the POST but offered no cart destination to inspect, adjust, or remove that item. This gap could be addressed without creating orders, charging money, or contacting payment providers.

**Changes:**

- Added `CartScreen.kt`, reachable from the signed-in app header. It loads the server cart, renders item name, variant/store, unit price and server total, supports refresh, quantity decrement/increment, and removal. It states checkout is not available in Android rather than presenting a nonfunctional purchase button.
- Extended `CartRepository.kt` for authenticated GET, PATCH quantity, and DELETE item requests. Identifiers and quantity are validated; no API origin or commerce values are hardcoded. Failures are translated to safe retry/session messages.
- Added repository tests for response parsing, exact HTTP paths/methods, authentication gating, and input validation; added Compose UI coverage for cart rendering and quantity/remove request sequence.
- Added a named cart action in the app header, preserving the existing dirty `NanttyApp.kt` edits and limiting modifications to the needed insertion points.

### Payment verification polling parity — 2026-11-05

The prior pending/manual-recheck limitation is now closed at source level. After the hosted-payment screen resumes, and when the buyer manually checks, Android calls the existing server verification endpoint every 3 seconds for up to 120 seconds, matching React Native's polling window. A `ConnectivityManager.NetworkCallback` tracks validated default-network changes; polling pauses while offline and extends the deadline by the offline interval. Transient verification failures are retried, while explicit server `paid`, `failed`, and authentication-required results terminate polling distinctly. Leaving the payment screen cancels further checks and unregisters the callback. Only the server's `paid` result exposes order confirmation; provider return is never treated as payment proof.

`PaymentStatusPollerTest` covers pending-to-paid, explicit server failure, offline recovery/deadline extension, transient failures and timeout, cancellation, and auth termination. Validation passed on the current tree: Kotlin compile, the 5 focused poller tests, Android-test-source compile, `:app:lintDebug`, and `git diff --check`. The lint task exited successfully, though the SARIF reporter logged a quick-fix-generation warning for the existing `Uri.parse(payment!!.checkoutUrl)` suggestion. No emulator/provider round trip or live API test was run. Further purchase parity gaps listed above remain open.

### Seller order-status correction — 2026-11-05
