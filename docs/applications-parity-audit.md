# Nantty application correspondence audit

**Snapshot:** 2026-11-03

**Method:** source/configuration review plus focused typecheck and lint. This is not a claim that every end-to-end flow has been exercised against a running backend.

## What “corresponding” means

Nantty has several distinct applications, not one UI copied into every target. The buyer/social clients (React Native, webapp, native Android, native iOS) should converge on the same user-facing capabilities and backend contracts while using platform-appropriate navigation and controls. Seller, creator, Ads, Admin, and public marketing apps have different audiences and should correspond to their own service permissions and product policies; they should not duplicate unrelated consumer features.

The app directory inventory is: `apps/mobile`, `apps/webapp`, `apps/native/android`, `apps/native/ios`, `apps/web`, `apps/seller`, `apps/studio`, `apps/ads`, and `apps/admin` (including its Tauri shell). The read-only route audit enumerated 109 webapp page files and 124 React Navigation registrations. Routes were exhaustive as registries; behavior was sampled across feature families.

## Confirmed correspondence gaps

### P1 — Verification checkout contract is incomplete

The web verification UI expects the application response to include `checkoutUrl` and redirects the user there. The Go submission handler returns only `applicationId`; it persists `DocumentUrls`, not a distinct selfie/document evidence model. The React Native development purchase sheet describes store billing/renewal, but confirmation only submits the application. This is a source-confirmed UI/API mismatch; actual payment behavior was not tested.

**Disposition:** do not paper over this with a fabricated checkout URL or claim the store purchase sheet performs IAP. Define and implement the approved provider workflow, identity evidence persistence, consent, authenticated payment confirmation and idempotent activation before exposing checkout promises.

**Safe web correction (2026-11-03):** the consumer-web Verification page no longer posts placeholder `"web"` document/selfie values or redirects to a checkout URL that the endpoint does not return. It shows plans as informational and links to the existing identity-verification hub for actual evidence capture and eligibility-gated checkout. The unused web service method and checkout response type were removed. Webapp TypeScript and focused ESLint passed using already-installed local binaries; pnpm itself was blocked by its existing Expo package trust-downgrade policy. The Go endpoint and React Native service/mock still retain the legacy application/checkout contract, so this finding is only partially resolved and the mobile path still requires a proper native-store/payment contract review.

### P2 — Managed-profile comments lose the displayed identity in post threads

The backend comment view includes `postedAs`. The clip-comment surfaces use the managed profile name/handle/avatar/checkmark; post-thread rows previously rendered the personal author identity. This conflicted with the requested “comment as” behavior.

**Implemented this turn:** post-thread rows in webapp and React Native now display the managed profile attribution and applicable badge while retaining the underlying author identity for ownership/authorization decisions. A managed profile is not made into a user-profile link unless a supported profile route is known.

**Verification:** webapp and mobile TypeScript checks and focused ESLint passed. No seeded managed-profile API/browser/device test was available, so the rendered live response remains unverified.

### P2 — Web HLS-only playback gap

Web source selection only plays HLS where the browser offers native HLS. An HLS-only asset in a browser without native HLS support falls back to its poster; React Native passes HLS to Expo Video. Progressive video is preferred on web when supplied, so this gap affects HLS-only records.

**Disposition:** confirmed source-level gap; no new streaming dependency was added in this audit. A follow-up should choose an approved HLS.js integration (MSE-capable browsers), retain native playback where available, surface a real unsupported/error state, and verify CORS/codec behavior on representative browsers.

### P2 — Seller sales chart accuracy and small-screen fit

The React Native chart used hard-coded hour labels, fixed dollar-like tick values, bars scaled to an arbitrary multiplier, a fixed width, and an accessibility label calling sales amounts “orders.” The web seller chart uses server labels, store currency and a readable series.

**Implemented this turn:** the mobile chart now uses the backend series labels and store currency, scales bars against the returned series, describes sales rather than orders to assistive technology, and scales its width to the current window up to its design maximum. The screen now passes the actual server series and total-sales money value.

**Verification:** mobile TypeScript check and focused ESLint passed. Device rendering and screen-reader behavior were not tested.
