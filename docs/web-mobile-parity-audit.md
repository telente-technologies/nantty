No app services were started, and no production or customer data was used. “API-backed” below means the client calls an application API route; it does not assert that the remote service was available or that the flow was exercised end to end.

## Feature parity vs responsive/layout parity

- Story traversal was already present in the current working tree at the start of this pass: web follows the story tray across users in either direction and continues video stories when playback ends. Its unit tests are included in the working tree.
- The concrete UI parity mismatch fixed in this pass was the primary feed action order; web now matches the mobile Like, Reply, Repost, Views sequence. Action behavior and API calls were not changed.
- Multi-media web posts now mount the existing inline player only for the selected direct-video slide. Changing slides unmounts the previous player; direct video controls/fullscreen are inherited from the shared player. HLS playback remains a poster fallback.
- The inbox now mirrors mobile’s Stories entry point using the existing story-tray API and `/create/story` / `/stories/:userId` routes. The rail is horizontally scrollable and remains in the desktop inbox pane when a conversation is selected; it is omitted from Requests and Spam folders. Existing conversation-list polling, message services, encryption, and split-pane behavior were not changed.
- Encrypted Story replies and their responsive web composer were already present in the current branch; they were verified by source inspection and the existing service test, not implemented in this pass.
- The seller dashboard now offers the same six time filters as mobile. Both clients pass the selected period through the same `period` query parameter to `/api/v1/seller/dashboard`; this does not add a new endpoint or change dashboard data behavior.
- The web seller dashboard now mirrors mobile’s “Post as store” behavior: call authenticated `PUT /api/v1/users/me/acting-profile` with the linked `storeId`, cache the returned profile, then route to `/post/new`. `PostComposer` fetches the current server acting profile, displays the selected identity, waits for profile confirmation before enabling publish, and includes `asProfileId` in the existing `POST /api/v1/posts` payload. The backend continues to authorize profile ownership/postability; the browser’s `storeId` is not treated as proof. Loading is reflected in the disabled/busy button and failures are announced as an alert. Both web and mobile mock post creation now preserve the signed-in account as `author` and represent the store separately as `postedAs`, matching the backend `PostView` shape. This is API-contract/source-tested, not a live backend session.
- Mobile’s full-screen/safe-area viewer and tap/gesture zones remain intentionally different from web’s contained viewer and accessible buttons. Browser/device visual QA was not performed.
- Desktop messaging’s split-pane inbox is intentionally different from mobile’s single-screen conversation stack; both use the same underlying conversation/service model in the sampled code.
- **Focused follow-up audit (2026-11-02):** direct-video playback in a multi-item web carousel is present in current source: `PostMedia` mounts `InlineVideoPlayer` only for the active video slide and unmounts it when another slide becomes active (`apps/webapp/src/components/feed/postCardMedia.tsx`; regression helper/tests at `postCardMedia.util.ts` and `postCardMedia.test.ts`). The feed now prefers HLS on browsers with native HLS and falls back to the progressive primary URL on browsers without native HLS or after HLS playback errors (`selectPostVideoSource`). The media processing path returns both a progressive primary variant URL and `hlsUrl` when available (`services/typescript/social/src/integrations/httpMediaDescriptorResolver.integration.ts`, `services/typescript/social/src/modules/contentEvents/commands/applyProcessedMedia/applyProcessedMedia.handler.ts`). HLS-only media with no progressive URL still needs native-HLS browser support; this is an explicit limitation, not evidence of cross-browser HLS.js playback. The desktop chat split pane is verified in source at `apps/webapp/src/app/(app)/chats/layout.tsx`; mobile intentionally navigates from its inbox list to a single chat screen. No additional desktop messaging mismatch was confirmed in this bounded sample.
