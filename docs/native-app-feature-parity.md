# Native app feature parity map

## Scope

This is a source-based orientation for planning native Android/iOS work against the existing React Native app (`apps/mobile`) and Next.js web app (`apps/webapp`). It samples navigation, representative screens, and service/API boundaries for major product areas. It is not a route-by-route audit, runtime comparison, or confirmation that every listed flow works against production services. Presence in source can include mock-backed states; confirm each flow's data source and end-to-end behavior before treating it as shipped parity.

## Native Android and iOS status in this checkout

- **Android (`apps/native/android`)**: independent Kotlin/Jetpack Compose app, not a web or React Native wrapper. `NanttyApp.kt` renders a responsive shell with Home, Discover, Activity, Messages, and Profile destinations, but only Home has content; the other destinations show “coming to the native app.” The Home feed calls the optional-auth `GET /api/v1/feeds/for-you?limit=10`, parses author/posted-as details and ready media, and displays images or video posters plus read-only engagement counts. No sign-in/token flow, engagement actions, or authenticated following feed is present. `README.md` documents API-origin configuration and that the following feed is not exposed yet. The Glance widget is currently a branded app-launch card, not a live feed widget.
- **iOS (`apps/native/ios`)**: independent SwiftUI app plus WidgetKit extension, not a wrapper. `AppShell.swift` has For You and Settings destinations; For You reads the optional-auth `GET /api/v1/feeds/for-you` using async `URLSession` and displays author handle, post text, attached images, loading/empty/error/retry and pull-to-refresh states. It currently lacks feed pagination, post interactions, author avatars and authenticated/following flows. `APISettingsView.swift` stores the backend URL. The widget reads a configured Boolean from the app group and makes no network request; it is a configuration-status widget, not a live feed widget. `README.md` explicitly says broader social and marketplace workflows are not implemented.
- **Build/runtime qualification**: Android's Gradle unit-test task was attempted with Java 21 and stopped during configuration because the Android SDK location is not installed/configured (`ANDROID_HOME` and `ANDROID_SDK_ROOT` unset); no Android tests or APK build are verified. Swift, Xcode, and XcodeGen are unavailable, so the iOS project cannot be generated or built here. Neither target has been installed or exercised on a device or emulator.

## Known divergences to carry into planning

1. Native scope is far smaller than either existing app: Android has an anonymous read-only For You feed and placeholder destinations; iOS has an anonymous read-only For You feed and Settings, without posting or engagement actions.
2. Existing mobile and web surfaces are not automatically equivalent to each other. Their navigation, layout, platform integrations, and potentially supported actions differ; compare behavior at flow level.
3. Fixtures and mocks exist in both app trees. A screen or component is evidence of source presence, not proof of live backend wiring or production availability.
4. Both native feeds are anonymous reads only; the native targets omit the authenticated/personalized following feed and all posting, reply/thread, like, repost, messaging, marketplace, wallet, creator/seller, verification and safety workflows. The native widgets are launch/configuration cards, not equivalents of the existing mobile widgets.

## Phased mapping approach

1. **Inventory contracts:** for each area, select the user-visible flow and trace screen → service → API contract, recording auth requirements, mock/fallback paths, platform permissions, and externally handled steps.
2. **Set native slice criteria:** choose a small read-only or low-risk flow first; define loading, empty, error, accessibility, deep-link, and offline expectations for Android and iOS separately.
3. **Map interaction and state:** document actions, navigation destinations, persistence, realtime/background behavior, and server-owned invariants. Mark intentional platform differences explicitly instead of forcing visual parity.
4. **Implement and verify by slice:** build both native implementations against shared API contracts where appropriate; validate source contracts, builds, and representative device flows before marking a row complete.
5. **Track coverage:** maintain per-flow status (`not mapped`, `mapped`, `implemented`, `verified`) and evidence links. Expand to authenticated social, commerce, wallet, messaging, creator/seller, and trust flows only after prerequisites such as identity, payments, and native permissions are understood.
