# Native app feature parity map

## Scope

This is a source-based orientation for planning native Android/iOS work against the existing React Native app (`apps/mobile`) and Next.js web app (`apps/webapp`). It samples navigation, representative screens, and service/API boundaries for major product areas. It is not a route-by-route audit, runtime comparison, or confirmation that every listed flow works against production services. Presence in source can include mock-backed states; confirm each flow's data source and end-to-end behavior before treating it as shipped parity.

## Native Android and iOS status in this checkout

- **Android (`apps/native/android`)**: independent Kotlin/Jetpack Compose app, not a web or React Native wrapper. It has sign-in, refresh-token rotation, authenticated logout, and encrypted session persistence; the AES-GCM key is held by Android Keystore, passwords are not persisted, and tokens are not shared with widgets. The feed has For You and Following tabs; Following calls authenticated `GET /api/v1/feeds/following`, refuses requests without a session token, and reports a rejected session rather than falling back to public content. Both feed types use cursor continuation, deduplication, retry, and an explicit end state. Feed cards open an API-backed post detail/thread view with recursive replies and ready image/video-preview media; signed-in users can reply at nested levels and Like/Unlike or Repost/Undo from feed/detail. The thread shows a subdued “Nantty for Android” label once above its post and replies. A text-only authenticated composer calls `POST /api/v1/posts` with a stable retry idempotency key. Global Discover supports guest and signed-in Top/Posts searches via `GET /api/v1/search`, cursor paging, loading/error/empty/retry states, and only opens validated post results in the existing thread destination. Other result types, scoped/recent search, and parity with every mobile result card remain incomplete. Saved supports authenticated, cursor-paged posts and post-backed videos through `/api/v1/saves?type=post|video`; malformed UUID cursors/IDs and mismatched post targets are rejected or ignored. Its Posts/Videos filters, loading/empty/error/retry states, and thread routing are present; clips, products, replies, and collections remain absent. A read-only Wallet destination calls account-scoped `GET /api/v1/wallets/me` and cursor-paged `/api/v1/wallets/me/transactions` through the encrypted session boundary; it presents server balance lines, coin balances, verification guidance, recent transactions, and loading/error/retry/empty states, but no payment or payout mutations. There are separate responsive Glance home-launch and Orders widgets. The Orders host fetches `/api/v1/widgets/orders` with the normal session, saves only a small count/status snapshot for the widget, refreshes on app foreground/session restore and periodically through WorkManager, and clears it at sign-out. Activity is partial; Messages, Profile, media publishing, scheduling, and business-profile posting remain incomplete/placeholders.
- **iOS (`apps/native/ios`)**: independent SwiftUI app plus WidgetKit extension, not a wrapper. It has sign-in/account, refresh-token rotation, current-user fetch, authenticated logout, and device-only Keychain token storage; credentials are not placed in UserDefaults or the widget app group. The adaptive feed selector provides public For You and authenticated Following (`GET /api/v1/feeds/following`). Following is gated in the view, `SessionModel`, and `FeedService`; no request is sent signed out, bearer credentials are loaded only through the Keychain-backed session boundary, expired sessions are cleared, and feed state/late responses are discarded across feed or account changes. Both feeds use server cursor continuation, duplicate removal, and accessible loading/retry/empty/end states. Feed rows expose authenticated Like/Unlike and Repost/Undo actions through `SessionModel`, update counts only on successful responses, and route guests to Account without sending a write. Signed-in users can create text-only posts through authenticated `POST /api/v1/posts`. Explore supports guest and signed-in global Posts search via `GET /api/v1/search`, cursor paging, stale-request suppression, and validated navigation only for supported post results; other result types, scopes, and recent terms remain missing. Selecting a post opens an API-backed detail/thread view with recursive replies, ready image attachments and backend `videoReplies` poster previews, authenticated top-level/nested replies, and Like/Unlike and Repost/Undo actions; the thread shows a subdued “Nantty for iPhone” line once above the post and replies. Saved Posts uses the Keychain-backed `SessionModel` for authenticated, cursor-paged `GET /api/v1/saves?type=post`, with sign-in, loading, empty, error/retry and refresh states and navigation to the existing thread. It intentionally does not claim parity for saved videos, clips, products, replies, or collections. A read-only Wallet destination calls `GET /api/v1/wallets/me` and `/api/v1/wallets/me/transactions` through `SessionModel`'s Keychain boundary; it shows balance lines, spendable/earned coins, verification guidance, and cursor-paged recent activity with signed-out/loading/error/retry/empty/end states and pull-to-refresh. It does not provide payment or payout mutations. WidgetKit has both an adaptive app-launch widget and an Orders widget. The host refreshes order data through the Keychain session and shares only a bounded snapshot through the App Group; the extension is cache-only, marks content privacy-sensitive, handles unavailable/stale/signed-out states, and links to the native Orders view. Thread pagination, media publishing/playback, scheduling, messaging, and seller/creator workflows are not implemented.
- **Build/runtime qualification (historical checkpoint, 2026-11-03)**: an earlier Android `:app:testDebugUnitTest :app:compileDebugAndroidTestKotlin :app:assembleDebug` run passed with 133 JVM tests. Later dated entries below record newer suites and changes; do not use this checkpoint as the current test count. No emulator/device UI or accessibility test ran. On iOS, `swiftc -frontend -parse` passed for app, widget, shared, and test Swift files, but that does not typecheck SwiftUI or compile the app; Xcode/XcodeGen are unavailable, so XCTest, app/WidgetKit builds, simulator, and iPhone Duo validation remain unverified. ## Phased mapping approach

1. **Inventory contracts:** for each area, select the user-visible flow and trace screen → service → API contract, recording auth requirements, mock/fallback paths, platform permissions, and externally handled steps.
2. **Set native slice criteria:** choose a small read-only or low-risk flow first; define loading, empty, error, accessibility, deep-link, and offline expectations for Android and iOS separately.
3. **Map interaction and state:** document actions, navigation destinations, persistence, realtime/background behavior, and server-owned invariants. Mark intentional platform differences explicitly instead of forcing visual parity.
4. **Implement and verify by slice:** build both native implementations against shared API contracts where appropriate; validate source contracts, builds, and representative device flows before marking a row complete. Android composer unit/Compose tests are authored but not yet compiled or executed because this host has no configured Android SDK. iOS XCTest source covers composer validation, session enforcement, and the authenticated idempotent request contract, but cannot run here because Swift/Xcode/XcodeGen are unavailable.
5. **Track coverage:** maintain per-flow status (`not mapped`, `mapped`, `implemented`, `verified`) and evidence links. Expand to authenticated social, commerce, wallet, messaging, creator/seller, and trust flows only after prerequisites such as identity, payments, and native permissions are understood.

## Native platform design and release gates

- **iOS:** use SwiftUI standard navigation containers, toolbars, and system controls; let Liquid Glass distinguish navigation/control chrome from content instead of applying a glass treatment to every card. Layouts must derive from available container geometry and size classes, respect iPhone Duo fold/camera reserved regions and vertical toolbar placement, and be exercised closed, open, and partially folded in supported orientations. References: [Apple Technology Overviews](https://developer.apple.com/documentation/technologyoverviews/), [SwiftUI](https://developer.apple.com/documentation/technologyoverviews/swiftui), [iPhone Duo preparation](https://developer.apple.com/documentation/technologyoverviews/preparing-your-app-for-iphone-duo), [Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/liquid-glass), and [App design and UI](https://developer.apple.com/documentation/technologyoverviews/app-design-and-ui).
- **Android:** derive layout from the app window and adaptive size classes; change navigation/pane structure where useful instead of merely stretching phone layouts. Test fold postures, resizable/multi-window layouts, keyboard/pointer and accessibility behavior, and widget sizes. References: [Android getting started](https://developer.android.com/get-started/overview), [Android UI design](https://developer.android.com/design/ui), and [Compose adaptive layouts](https://developer.android.com/develop/ui/compose/layouts/adaptive).
- **Release gate:** authored source tests do not count as a native build or device pass. Before calling a platform production-ready, run clean builds/tests with supported SDKs, exercise phone/tablet/foldable configurations, verify screen-reader and keyboard paths, and validate real authenticated API flows against an isolated staging backend. Current host limitations are listed above; no native build/device gate has passed yet.
