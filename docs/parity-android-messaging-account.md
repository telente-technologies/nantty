# React Native ↔ Kotlin Android: messaging and account parity audit

**Audit date:** 2026-11-04  
**Scope:** conversations/chat/groups/settings, profile/edit/connections, account/security/privacy, notifications. Auth flows are explicitly excluded. This is a source audit of the current fork; it does not assert live-service behavior.

## Status legend and method

- **Implemented** — a reachable Kotlin screen/flow and its service contract cover the RN behavior in this audited slice.
- **Partial** — a native slice exists, but one or more RN behaviors, screen affordances, or service operations are absent.
- **Missing** — no corresponding reachable Kotlin screen/flow and service operation were found.
- **Intentional** — a source comment/product rule explicitly defers the behavior. No intentional deferrals were found for the missing rows below.

The RN reference is `apps/mobile/src/navigation/main.navigator.tsx`, `mainTabs.navigator.tsx`, and the cited screen/service implementations. Kotlin reachability is through `apps/native/android/app/src/main/java/com/nantty/android/ui/NanttyApp.kt`: `Destination` is limited to the app's current tab destinations at lines 116–118; `MainContent` connects profile, messages, and activity at lines 699–713. No general account/settings destination is registered there. Kotlin evidence below is from current source, not inferred from the UI design alone.

## One implemented gap: milestone notification preferences

Android previously exposed only the account-wide push toggle, even though the RN Notifications settings screen also exposes milestone push and email toggles. The native settings screen now loads the server category list and displays the `milestones` row only when it is returned, then sends only the changed field with the category. It disables writes while pending, honors `locked`, surfaces failures without optimistic state, and routes authentication-required failures through the existing reauthentication callback.

Implementation: `apps/native/android/app/src/main/java/com/nantty/android/data/AccountNotificationSettingsRepository.kt`, `ui/AccountNotificationSettingsScreen.kt`, and new `ui/MilestoneNotificationPreferences.kt`. Contract tests: `apps/native/android/app/src/test/java/com/nantty/android/data/AccountNotificationSettingsRepositoryTest.kt`; Compose coverage: `apps/native/android/app/src/androidTest/java/com/nantty/android/ui/MilestoneNotificationPreferencesTest.kt`.

## Implemented gap: follow-request review

React Native lists the signed-in account's pending requests through `GET /api/v1/users/me/follow-requests` and settles each using authenticated `POST /api/v1/follow-requests/{requestId}/accept|reject` (`apps/mobile/src/services/follows.service.ts`; `followRequests.screen.tsx`). The social service registers those routes with required authentication (`services/typescript/social/src/modules/follows/routes/follows.routes.ts` and `controllers/follows.controller.ts`).

Android now links a private profile's “Review follow requests” action and `followRequest` Activity notifications to a paged Compose flow. Notification routing gives this `kind` precedence over a post fallback, as in RN. System Back returns from the standalone inbox to Profile; the profile-embedded inbox retains its local Back behavior. Requester identity is a labeled, focusable action that opens the existing public-profile route. Confirm/Delete actions remain server-authoritative; a request disappears only after a successful response. The screen is width-constrained on larger windows and exposes contextual action/loading labels. The repository encodes cursors and request IDs, maps only the public requester summary, bounds response reads, and reports auth failures for reauthentication. Contract tests cover authenticated paths, paging, malformed/private fields, and non-call behavior for missing session/unsafe IDs. Instrumentation-test sources cover list/accept, requester navigation, and notification routing; they are compiled, not device-run. |

Connection tabs, search/sort, relationship filters, and the row action that starts a direct conversation and opens its thread are present; username navigation remains missing. Notification target gaps also remain: Kotlin does not preserve specific conversation/message targets and cannot safely route clips/comments, verification, support tickets, URLs, and arbitrary screen references until matching native routes and safety rules exist. Those were intentionally left unimplemented rather than pointed at the wrong screen. Announced action success/failure states and connected-device accessibility verification remain outstanding.

## Delta — 2026-11-05: Android channel creation

React Native creates a broadcast channel through `apps/mobile/src/screens/messages/newGroup.screen.tsx` and `apps/mobile/src/services/social/channels.service.ts`. The Social service already mounts authenticated `POST /api/v1/channels`; its schema accepts a name up to 80 characters, an optional description up to 500 characters, and an optional media ID. The handler creates an owner membership and returns the canonical `ConversationView`.

Android now exposes an accessible Create broadcast channel action in `MessagesScreen.kt`, a bounded/scrollable Compose dialog in `CreateChannelDialog.kt`, and `MessagesRepository.createChannel` sends only trimmed name/description to that existing endpoint. It validates lengths locally, refreshes the session once on 401, maps the returned channel, refreshes the inbox, and opens the resulting thread. The dialog explicitly tells users that channel posting is not available on Android until encrypted messaging compatibility is complete; the thread remains read-only and does not reveal plaintext or ciphertext.

Repository tests cover the authenticated path/body, response mapping, blank-description omission, and local input rejection; instrumentation source covers the action-to-API-to-read-only-thread flow. A Social route test covers authentication, ownership mapping, limits, and optional media handling (2 tests pass). Group creation and channel photo upload are still absent on Android. No Go backend route was required: this endpoint is implemented in the TypeScript Social service. Channel subscription and posting remain separate parity work. Android UI test source compiles, but device execution has not been performed.

## Android design and architecture notes

The Android docs emphasize scalable, modularized, testable Kotlin/Compose apps, consistent quality across form factors, and layouts/adaptive interactions for phones, tablets and foldables. The existing native UI already uses Compose and window-size/hinge-aware layout in the shell, but parity is feature-flow based, not achieved by copying RN pixels. Continue using Material controls, accessible names/states, server-owned preference values, and adaptive width/layout behavior. # Group/channel invitations — in progress (2026-11-05)

The current worktree now contains a backend-owned, recipient-scoped **group invitation** foundation: create by account ID, received/sent cursor list, accept/decline, revoke, seven-day expiry, and a `preventDirectGroupAdds` chat setting that rejects unsolicited direct additions. The setting is exposed in React Native, web, and Kotlin Chat Settings. Each loads the server boolean and adopts the PATCH response; the controls do not optimistically flip it. RN row tests **3/3**, web service tests **10/10**, Kotlin repository tests, and Compose instrumentation test source cover the setting. Kotlin unit tests, production compile, and Android-test-source compile pass; Compose instrumentation is not device-run because no emulator is available.

Important E2EE boundary: accepting currently records consent but does **not** create group membership; the API reports `awaiting_secure_key_handoff`. This is intentional until a secure key handoff and history-access policy are implemented. Do not present accepted as joined or expose group history.

Still missing from verified current source: unique invite links with expiry/revocation; channel invite/subscribe acceptance; end-to-end key handoff; web group-invitation inbox/action parity; and service/migration deployment verification. The backend direct-add preference does not yet imply that channel direct subscription is protected. Group invitation in-app/push mappings are implemented, but actual provider delivery, retry, and per-client notification deep-link behavior remain unverified. The goal remains open until these contracts and client flows are implemented and tested.
