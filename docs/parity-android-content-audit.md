# React Native ↔ Android content parity audit

Scope: feed, content creation, post detail/replies, clips, stories, live, and Spaces. This audit compares the RN navigation/screen/service surface with the current Kotlin Compose navigation and data/UI surface. It does not cover messaging or seller/creator/brand/ads workspaces.

Latest Android source-size check (2026-11-06): **375 Kotlin files** (236 production, 87 JVM test, 52 instrumentation-test sources); none exceeds 500 lines. `SignedInApp.kt` is 456 lines after extraction of `SignedInFeedController` from its 508-line state. The extraction preserves saveable feed selection and generation-based stale-response checks; dedicated controller tests cover guest gating, topic selection, and stale refreshes. Full verification details are recorded in `docs/react-native-android-parity-audit.md`.

## Historical delta — 2026-11-05: Space coin donations (superseded by checkpoint below)

The following initial notes record an earlier implementation state. Later dated deltas supersede historical statements where noted.

- RN and web send an explicit `giftsEnabled` preference at Space creation and expose a host-only setting for live/scheduled Spaces. Go persists that value and mounts authenticated, idempotent `PATCH /api/v1/spaces/{spaceId}/coin-donations`. Omitted preference now defaults to off, and RN does not infer donation permission from creator status; legacy sessions without the host setting remain non-donatable until the host opts in.
- Space contributions have moved to amount-only `POST /api/v1/spaces/{spaceId}/coin-donations` (`{"coins": positiveInteger}`). The money service resolves the host and creator share server-side; policy bounds are configured with `SPACE_COIN_DONATION_MIN_COINS` / `SPACE_COIN_DONATION_MAX_COINS`; the debit, creator/platform ledger credits, earning, donation record, and outbox event are transactionally recorded. The old Space SKU endpoint is no longer mounted. Other live-stream gift routes are separate and unchanged.
- RN and web now use coin amount entry rather than virtual gift catalogs. The web mock uses the shared mock coin balance and debits donations instead of returning a fabricated balance.
- Kotlin `SpacesModels` / `SpacesRepository` and repository contract tests have been added; the Compose destination/navigation is now implemented as described in the later checkpoint. The iOS SwiftUI app still has no Spaces destination. Android LiveKit audio is not implemented; do not treat the REST join grant as a connected audio session.
- At the time of this historical note, role invitations and Kotlin reporting were incomplete; see the later checkpoint for current implementation and remaining client/push gaps.
- Creator policy currently uses server-owned real-follower, account-age, posting, violation, and risk/fraud signals. It does not have verified-follower counts or time-windowed organic impression data, so those requested thresholds cannot yet be safely evaluated. Seller country enforcement currently depends on account/profile country data; it is not proof of verified residence/nationality. Buyer checkout has no blanket Nigeria-only restriction but remains bounded by available seller shipping destinations and currency support.
- Focused verification so far: Spaces service tests pass in RN (**7/7**); web contract suite passes (**154/154**); Go live sessions controller/routes pass; creators LiveMoney service/model tests pass; creator-program service tests pass. The creator donation DB integration test could not connect to the configured local Postgres, and migrations have not been applied. Android UI/build verification is pending completion of the in-progress Compose integration; no device run or production round trip is claimed.

## Implemented parity fix: post audience privacy

RN `PostToolbar` (`components/create/postToolbar.tsx`) toggles the audience between `everyone` and `followers`, and `CreatePostScreen` passes that value to the create-post mutation. Android previously hardcoded `audience: "everyone"` in `PostComposerRepository`, leaving no way to publish followers-only text.

Android now exposes the same two options in the Compose composer, submits the selected wire value to the existing `POST /api/v1/posts` body, keeps `everyone` as the backward-compatible repository default, and rotates the idempotency key when audience changes so a retry key is not reused for a different payload. No API, auth, or server policy was changed.

Coverage added to `PostComposerRepositoryTest` and `PostComposerScreenTest` for followers-only serialization and the UI-to-request flow.

### Historical audit — 2026-11-05: Space invitation recipient response audit (superseded)

The findings below were accurate before the recipient-scoped read contract and client recipient flows were implemented. Do not use the “absent” findings as current status; see the 2026-11-06 update below.

- Go mounts authenticated/idempotent `POST /api/v1/spaces/{spaceId}/invites/{invitationId}/accept` and `/decline`. `RespondToSpaceInvitation` authorizes the acting account against the stored invitation account ID, persists the status, and emits `space.inviteAccepted` / `space.inviteDeclined` outbox events. The invitation metadata contains IDs, account IDs, roles, optional titles, statuses, and timestamps.
- The read contract required to present pending invitations is absent: `GET /api/v1/spaces` returns summaries; `GET /api/v1/spaces/{spaceId}` omits invitation metadata and only exposes `pendingSpeakerRequests` to moderators. There is no mounted “my pending Space invitations” route. The notification payloads currently parsed by RN/Kotlin expose post/conversation/message context, not `spaceId` or `invitationId`, and no consumer of the `space.invited` outbox event was found in the searched Go application tree.
- Consequently, neither mobile client can discover pending Space invitations without guessing IDs or scraping private metadata. RN `spacesService` and Kotlin `SpacesRepository` both support sending invitations, but neither has accept/decline client methods or a recipient UI. The response endpoints alone are insufficient to build a usable pending-invitation flow. No UI or client action was added; the blocker is the missing read/delivery contract, not merely screen wiring.
- Next backend contract needed before a client slice: an authenticated, paginated recipient-facing pending-invitations read (including `spaceId`, `invitationId`, role/title, inviter and Space summary), or an equivalent reliably delivered notification whose data contains those identifiers and can deep-link to the Space. This audit did not change backend/API schemas.
- Validation for this audit: source inspection of `sessions.routes.go`, `spaceInvite.controller.go`, `spacesDetail.controller.go`, `spaceInvitePolicy.service.go`, RN `spaces.service.ts`, Kotlin `SpacesRepository.kt` / `SpacesModels.kt`, and Kotlin `NotificationsRepository.kt`; `go test ./modules/live/src/modules/sessions/routes` passed; `git diff --check -- docs/parity-android-content-audit.md` passed. ### Historical delta — 2026-11-05: Recipient-scoped Space invitation read contract

- Added authenticated `GET /api/v1/spaces/invitations?cursor=&limit=` with the standard `{data,nextCursor}` envelope. Each result contains `spaceId`, `invitationId`, stored `role`, optional stage `title`, `invitedAt`, `inviterId`, and a safe Space summary using the existing mobile summary shape. Since the current mutation authorizes only the Space host to invite, `inviterId` is the Space host ID. It does not expose the recipient account ID or raw metadata.
- The query filters pending invitations by the authenticated account in SQL, excludes moderation-hidden Spaces, returns at most 100 entries per page (default 30), and uses an account-bound keyset cursor. The existing invitation JSONB array had no recipient lookup index, so the minimal migration adds a GIN `jsonb_path_ops` expression index on `metadata->'spaceInvitations'`; no invitation storage or write-path migration was necessary.
- Tests: unauthenticated route rejection and cursor/account binding unit tests pass. The Postgres-backed integration test also passed against the local ephemeral test schema, verifying summary shape, pagination, cross-account isolation, malformed timestamp handling, and an `EXPLAIN` plan using the GIN expression index with sequential scans disabled. The migration is exercised in the ephemeral test schema only; it has not been applied to a deployed database. No client changes were made.
