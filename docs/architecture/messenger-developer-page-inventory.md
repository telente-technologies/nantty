## Implemented authorization endpoints

Access-policy correction: organization membership alone never grants application access. Owners/admins can manage app metadata; other members can list/read only an application with an explicit `applications.read` grant that remains eligible for their current organization role. Requested product scopes are not management capabilities or authorization grants. Per-app grants are auditable and ineligible grants are pruned atomically after role downgrades. Future app resource handlers must enforce both current role eligibility and an explicit grant.

Messenger device authorization remains integrated through Go Identity. New installation identifiers use Expo Crypto `randomUUID()` instead of `Math.random()`; previously stored identifiers remain valid and are not forcibly rotated. Its canonical routes and proof handling are specified in [`messenger-auth-contract.md`](messenger-auth-contract.md).

The authenticated organization API exposes `GET`/`POST /api/v1/developer/organizations`; membership-scoped organization `GET` detail, `PATCH` update, access, roles, members, member detail, member `PATCH` role update and `DELETE`; owner-only step-up-protected `POST /{organizationId}/ownership-transfer`; owner-only `GET /{organizationId}/audit-log`; manager-only `GET`/`POST /{organizationId}/invitations`; invitee-only `GET /api/v1/developer/invitations` and `POST /{invitationId}` to accept/decline; manager-only `DELETE /{organizationId}/invitations/{invitationId}`; plus authenticated `GET`/`POST /{organizationId}/applications`, `GET`/`PATCH`/`DELETE /{organizationId}/applications/{applicationId}`, owner/admin `GET /{applicationId}/members`, and owner/admin `PUT /{applicationId}/members/{membershipId}/grants`. Owners/admins manage application metadata; ordinary members list/read only apps with an eligible `applications.read` grant; create requires a scoped 24-hour idempotency key; updates are draft-only; and each mutation is audited in the same transaction. The Developer BFF and Gateway allow only exact route/method pairs and reject unknown paths, malformed IDs, extra segments and unsupported verbs. The BFF forwards the idempotency key only for application creation. Requested scopes are candidate registration values only and never authorize API access. Applications archive rather than hard-delete. The transfer demotes the prior owner to Admin, promotes an existing member in a serializable transaction, and records the change atomically. The Next Developer BFF keeps access tokens server-side and proxies the short-lived step-up proof only for ownership transfer. Local sign-in can reuse the Nantty webapp cookie on `localhost` across ports. Production SSO is not configured because the main app uses host-only `__Host-` cookies; the Developer proxy returns an explicit unavailable status rather than broadening cookie scope or accepting a browser bearer token. Organization UI supports list/create, switching, details, access capabilities, member search/detail, authorized role changes/removal, owner-controlled name/slug updates, step-up-confirmed ownership transfer, owner-only audit events, and invitation management/recipient response. The application page performs real draft CRUD and owner/admin grant management while explicitly withholding credentials, approvals and API testing. Invitations are portal inbox only, not email. The organization access response remains organization-level; per-application grants are returned by the application member-grant endpoint; every future resource handler must enforce role plus an explicit grant. Fresh-schema Auth integration verified the organization, invitation, application and grant DB workflows against disposable Postgres. The related Identity migrations remain unapplied to persistent databases; Developer BFF/browser runtime, production SSO, downstream public API services and email delivery remain unverified or unavailable.

The per-application `GET /{organizationId}/applications/{applicationId}/capabilities/me` endpoint returns the authenticated member's actor UUID, application name and current effective capabilities: Owner/Admin role-eligible capabilities, or the intersection of member grants with current role eligibility. A fresh-schema integration verifies manager defaults, grant enablement, role-downgrade pruning, actor/application identity and archived-app denial. Gateway and Developer BFF allowlists are exact and authenticated. The Developer credential BFF checks this result before Sandbox control; only `ntsb_test_` credentials are available, and the schema-backed browser workflow remains unverified.

Organization update requires `organization.manage` (Owner/Admin), validates names/slugs, and records a before/after audit record in the same transaction. Audit reads require `security.manage` (Owner only) and return a bounded newest-first list. Team reads/mutations remain gated by `members.manage`; member endpoints disclose account ID, username, display name, role, status, and join time, not email addresses. Role changes accept only schema-supported roles, reject owner reassignment, and prevent Admin from granting Billing. Member removal locks the organization and membership rows, prevents removal of an owner or a role beyond the actor's grant authority, and audits in the deletion transaction. Ownership transfer requires a session-bound five-minute step-up token and explicit confirmation; it locks the organization and both memberships, updates both roles, and writes an audit event in one serializable transaction. A failed audit insert rolls back the mutation. The roles catalog reports the five assignable roles (owner, admin, developer, analyst, billing), not proposed roles absent from the schema. Creation requires an `Idempotency-Key`, replays the original result for 24 hours, and records creation. Invitations target existing active accounts with verified email, enforce role assignment policy, expire after seven days, appear in the authenticated invitee inbox, require explicit accept/decline, support manager revocation, and write audit events. No invitation email is sent. Pure role-policy tests and Gateway route tests pass. Identity migrations for organization, membership, idempotency, audit, invitations, applications and application grants remain unapplied; database-backed verification is therefore outstanding. The invitation integration test was skipped because the configured local Postgres endpoint is unavailable/authentication-failing. Application-grant code and UI exist but database verification remains open; downstream resource services, production SSO, and cross-environment authorization also remain open. No credentials, webhooks, billing, logs, sandbox execution, or public messaging operations were added. Existing public Business Messaging routes remain proposals until owner services, OpenAPI contracts, permissions, quotas, and isolation tests exist.
