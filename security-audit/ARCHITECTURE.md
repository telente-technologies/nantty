# Architecture and trust boundaries

This map is derived from current manifests, gateway routing, service directories, Dockerfiles, Terraform modules and local compose; it is not inferred solely from product documentation.

## Runtime layers

- **Clients:** Next.js web, webapp, seller, admin, Ads and Studio apps; Expo/React Native mobile. Public marketing pages have static-export build paths.
- **Public API edge:** AWS ALB/WAF forwards `/` traffic to the TypeScript Fastify gateway and `/ws*` to Phoenix realtime. Gateway routes requests by explicit path/method policy; JWT verification uses the identity JWKS, and the gateway signs internal identity context for upstream services.
- **Go deployables:** identity, commerce, money, live, ads and trust. Go modules include auth/users/catalog/inventory/orders/payments/wallet/ledger/escrow/subscriptions/creators/live/moderation and supporting modules. Money handles Flutterwave-facing flows; ledger is the accounting source of record.
- **TypeScript deployables:** Fastify gateway, social, notifications, media, search and support.
- **Other services:** Python intelligence (internal signed requests/events) and Elixir/Phoenix realtime (WebSocket/event delivery).
- **State and async:** Aurora PostgreSQL/RDS Proxy; Valkey; RabbitMQ/Amazon MQ; S3 and CloudFront signed/private media; SES/SQS; optional LocalStack, SeaweedFS, LiveKit, OpenSearch and ClickHouse in local compose.
- **Infrastructure:** Terraform has dev/staging/prod configurations and reusable AWS modules for VPC, ALB/WAF, ECS, Aurora, storage/CDN, KMS, Valkey, MQ, SES, observability, GitHub OIDC and backups. CI builds/scans service images and stages migration/snapshot gates before deployment.

## Trust boundaries and sensitive flows

1. **Browser/mobile → edge/gateway:** untrusted request bodies, bearer/session tokens, user-controlled object IDs and upload metadata. Gateway is expected to enforce token verification, route auth, admin/staff policy, CORS, rate limits, body caps and internal-path denial.
2. **Gateway → service:** internal signed identity context and service-specific bearer/shared tokens over private service networking; AWS config includes a TLS proxy/service identity path. Confirm deployed certificates, endpoint DNS and runtime secret rotation operationally.
3. **Service → database:** per-service PostgreSQL roles and schemas, with money modules sharing a deployable role. Ledger correctness relies on database permissions, transactionality, idempotency constraints and append-only controls.
4. **Service → queue/cache:** asynchronous outbox/event delivery and rate/session state. Queue ACLs, poison-message behavior, replay handling and cache outage behavior require live isolated validation.
5. **Payment provider → webhook ingress → money:** raw webhook bytes and signature/hash header must be preserved and verified; provider event handling must be idempotent and reconciled against local state.
6. **Client → media storage/CDN:** authenticated upload intent, short-lived presigned PUT/chunk URLs, private quarantine, processing/moderation, derivative storage and time-limited signed downloads.
7. **Staff/admin → gateway and services:** staff JWT, permission/step-up checks, network allowlist and audit recording. Terraform requires a non-empty admin IP allowlist outside dev.
8. **External processors:** Apple/Google billing validation, Smile ID, Turnstile, LiveKit and email provider. No live credentials or provider endpoints were exercised.

## Ledger database and migration path (verified from source, 2026-10-29)

- The `go-money` executable (`services/go/deployables/goMoney/server.go`) starts payments, wallet, ledger, escrow, subscriptions and creators modules in one ECS deployable. Those modules share the `MONEY_DATABASE_URL` connection pool path.
- Each money module's startup reaches `PrepareMoneyModuleResources` in `services/go/modules/ledger/src/loaders/moneyModule.loader.go`. That function calls `ApplyModuleMigrationsAsSchemaOwner` before opening the runtime pool. The migration helper scopes the URL to the module schema and sets PostgreSQL's startup `options=-c role=svc_<module>` (for ledger, `svc_ledger`) before applying the embedded `golang-migrate` files. Thus the runtime login is the shared `svc_money`, but the session assumes the per-schema owner role while it migrates.
- Local bootstrap (`infra/local/postgres/create-databases.sh`) creates `ledger` owned by `svc_ledger`, and grants `svc_ledger` membership to `svc_money`. This makes `svc_money` able to assume the ledger schema owner role. It separately creates `svc_migrator` only in the Aurora Terraform secret list; the local bootstrap does not create that identity.
- Aurora Terraform creates random Secrets Manager credentials for the listed role names, including `svc_migrator`, but does not create PostgreSQL roles, transfer schema ownership, or configure grants. `infra/aws/README.md` documents a manual role/bootstrap step and says `svc_migrator` owns schemas for migration tasks. Deployed grants/ownership are therefore unverified.
- `.github/workflows/deploy.yml` has staging and production pre-deploy snapshot gates followed by `runMigrationTask.sh`, which executes a separately named ECS task definition from GitHub environment variables, waits for STOPPED, and requires every essential container to exit 0 before service rollout. The task definition's command, environment, secret references and runtime DB identity are external to this repository and not proven here. Service task definitions currently inject only the `svc_money` `MONEY_DATABASE_URL` secret into `go-money`.
- Ledger migrations are embedded in `services/go/modules/ledger/src/migrations/embedded.migrations.go`; `golang-migrate` applies them under the schema search path and its PostgreSQL driver locking. The ledger tables include journal entries/lines, accounts, reconciliation rows, and outbox events. Runtime operations post balanced entries and read/update account balances/outbox state transactionally; database append-only triggers plus revoked UPDATE/DELETE/TRUNCATE protect journal history, but ownership can change that boundary.
- Existing service-role integration coverage (`ledgerPosting.serviceRole_integration_test.go`) tests DML posting and append-only UPDATE/DELETE refusals as `svc_money` and `svc_ledger`, but provisions test schema grants as a superuser and does not assert that the roles cannot perform DDL, SET ROLE into a migration identity, or change schema ownership. The normal local Postgres container is long-lived and treated as user data; it will not be repurposed for privilege tests.

The safe target is a distinct migration-only ECS task credential (not injected into `go-money`), a migration-owned ledger schema, explicit runtime grants on only the ledger operations needed, and no runtime membership in the owner/migrator role. Startup migration removal and the role/ownership rollout must be ordered so the task applies migrations before app deployment; production role state requires controlled bootstrap/verification and is not changed by this local work.

## Financial invariants to prove dynamically

- A provider event/charge/refund maps to at most one ledger settlement for its idempotency identity.
- Debits cannot make non-overdraft accounts negative; every posted journal entry balances by currency.
- Escrow release/refund/cancel paths are mutually exclusive, replay-safe and actor-authorized.
- Withdrawal reservations prevent concurrent requests from spending the same available funds.
- Seller inventory reservation and payment confirmation are atomic or recoverable without paid-but-unreserved orders.

These invariants were not dynamically re-proved in this run.

## Local remediation implementation and verification (2026-10-29)

The original section above describes the pre-remediation architecture and is retained as historical evidence. The current working-tree implementation has a `--migrate-money` one-shot path that validates the database username as `svc_migrator`, scopes each connection in turn to the six money schemas (`payments`, `wallet`, `ledger`, `escrow`, `subscriptions`, `creators`), strips role-changing `options`, and applies each embedded migration set through golang-migrate (PostgreSQL advisory locking remains provided by that driver). Normal startup migrations are disabled for all six modules. The deployment runner validates an environment-specific external ECS migration task family, requires only a `MONEY_MIGRATION_DATABASE_URL` secret whose reference denotes `svc_migrator`, rejects runtime DB URL env/secrets, replaces the image/entrypoint/command with the exact go-money release image and `--migrate-money`, and waits for all essential containers to stop successfully before rollout. Its tests use a mocked AWS CLI; no AWS call was made.

The final isolated PostGIS 17 test used loopback port 25432 and synthetic credentials/data, separate from the long-running development Postgres at 15432. All six money schemas/tables were owned by `svc_migrator`; `svc_money` was not a member of any module-owner/migration role and had schema USAGE but not CREATE across all six. Both logins lacked superuser, CREATEROLE and CREATEDB; `svc_money` was only a member of `nantty_readers`. The first runtime post exposed an FK failure: PostgreSQL's FK check uses the referencing table owner's privileges, and the append-only migration had revoked that owner's UPDATE. The forward migration grants only column-level `UPDATE(id)` back to the owner and revokes it from runtime; table-level UPDATE remains revoked and append-only triggers still reject journal edits. The focused runtime test passed balanced post, rollback, unbalanced-post rejection and account-balance assertions. All six migrations succeeded twice. The modified local bootstrap no longer defaults DELETE grants for ledger tables, and its shell syntax passed; the container's preseeded database/roles required creating the isolated test schema/role grants directly rather than running the non-idempotent whole bootstrap script end-to-end.

The full Go ledger package suite passed against the disposable database using the test/admin identity, including existing 40-way spend concurrency, 20-way idempotency replay and 72-way concurrent gift-posting invariants. The focused least-privilege runtime test confirms transactional posting under `svc_money`; isolated role/migration verification confirms runtime DELETE only on the three source-verified cleanup tables. The local bootstrap command was not proven end-to-end from pristine state in the final pass; isolated DB setup was direct before migrations. The Space route contract is source-tested; a live gateway-to-Go request remains unverified. Actual AWS roles, task definition, secret grants and workflow execution remain unverified. Full per-table SELECT/INSERT/UPDATE minimization is still open.

## Provider endpoint / egress inventory (source-only)

Configuration contains external HTTPS integrations including Flutterwave (`api.flutterwave.com`), Smile Identity (`api.smileidentity.com` and test API), Apple StoreKit/App Store, Google Android Publisher/OAuth/certificate endpoints, Cloudflare challenge endpoints, AWS service endpoints (including regional SQS), Expo push, and the configured media/CDN object-store paths. This is a source-derived candidate inventory, not a complete DNS/IP allowlist: several clients can override base URLs, AWS service endpoints resolve regionally, and test fixtures were deliberately excluded. No host was resolved or contacted. Current Terraform egress CIDR variables are empty by default and reject the all-IPv4 CIDR; static contracts pass. CIDR allowlisting alone is not a safe/maintainable hostname policy for several providers. An approved egress proxy or AWS private endpoints plus reviewed provider routing is still needed before runtime connectivity can be considered verified.
