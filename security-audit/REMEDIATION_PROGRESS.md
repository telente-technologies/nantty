## Verification record

- `python3 -m unittest discover -s security-audit/tests -v`: 5/5 passed.
- Final DB verification used disposable PostGIS PostgreSQL container `nantty-auddb-final-20261029`, loopback port 25432 and ephemeral storage; it was destroyed after tests. Existing development PostgreSQL at port 15432 remained running and untouched.
- Fresh isolated migrations for all six money schemas ran successfully and repeat invocation was a no-op. Runtime `svc_money` could not create/alter/drop schema objects, create/grant roles, or assume the migration/schema-owner roles; all six schemas allowed runtime USAGE but not CREATE. It had no DELETE on append-only journal tables and no TRUNCATE privilege. The migration-owned journal tables retain the required FK key-column permission for `FOR KEY SHARE`; table-level/runtime UPDATE remains revoked. `svc_migrator` is deliberately the privileged schema owner and must remain isolated to the migration task. The full local bootstrap was not proven end-to-end from pristine state in the final pass; isolated DB setup was direct before migration tests.
- After removing broad default DELETE, a new clean bootstrap and all-six migration pass confirmed that `svc_money` has DELETE only on `payments.provider_payout_destinations`, `creators.creator_brand_deals`, and `ledger.step_up_consumptions`; no other money table grants DELETE and no table grants TRUNCATE. Synthetic rows in those three tables were successfully deleted using the runtime identity.
- `NANTTY_RUN_LEDGER_PRIVILEGE_TEST=1 ... go test ./modules/ledger/src/modules/journal/services -run TestLedgerRuntimeRoleIsLeastPrivilegeAndTransactionsRemainAtomic -count=1 -v`: passed against isolated DB as `svc_money`; balanced posting, account balances, rollback, rejected unbalanced post, and append-only update denial verified.
- `MONEY_TEST_DATABASE_URL=<isolated admin URL> go test ./modules/ledger/src/...`: passed, including existing DB concurrency/financial tests (40 parallel spends: 10 accepted/30 rejected; 20 same-reference operations: one post/19 replays; 72 concurrent gift posts balanced). These concurrency tests ran with test/admin credentials, not `svc_money`.
- `NANTTY_RUN_MONEY_MIGRATION_TEST=1 MONEY_MIGRATION_DATABASE_URL=<isolated svc_migrator URL> go test ./deployables/goMoney -run TestMoneyMigrationRunnerIsRepeatableOnIsolatedPostgres -count=1 -v`: passed; all six schema migrations ran and repeated safely.
- `go test ./deployables/goMoney ./modules/ledger/src/loaders`: passed. `.github/scripts/runMigrationTask.test.sh` passed with mocked AWS only. Python static security contracts passed 5/5. Gateway route suite passed 110/110; Go Live suite passed. No live gateway-to-Go end-to-end request was possible.
- Escrow harness follow-up: full `go test ./... -count=1` passed in `services/go/modules/escrow` on disposable PostgreSQL after applying escrow migrations in the harness and correcting the underpayment fake-fee calculation. The focused payments underpayment webhook regression also passed. This validates local synthetic behavior only, not deployed service/provider behavior.
- The first runtime integration attempt exposed the FK failure. The append-only migration revoked UPDATE from the referencing table owner, but PostgreSQL performs FK `FOR KEY SHARE` checks using that owner’s privileges. A forward migration restores only owner column `UPDATE(id)`; the test then passed without giving the runtime role schema/migration-owner privileges.
- Broader auth/BOLA/payment/provider/webhook/upload/realtime/load testing was not completed because the full stack would reuse an existing development Postgres and local service ports; no independent full-stack disposable deployment configuration was available. No production or cloud state was accessed, and no commits, pushes or deployments occurred.
- The shared worktree contained 566 changed/untracked entries during this continuation; all unrelated/user work was preserved.
